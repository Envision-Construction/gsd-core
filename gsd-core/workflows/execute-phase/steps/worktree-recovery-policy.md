# Worktree Recovery Policy

## ORCHESTRATOR FAIL-CLOSED RULE (#48)

> **ORCHESTRATOR FAIL-CLOSED RULE (#48):** `worktree_branch_check` is verify-only — an executor that hits a base/HEAD-namespace mismatch prints `FATAL:` and exits **42** instead of self-recovering. If any executor result reports a `FATAL:`/`exit 42` (or its commits never appear because it halted at the check), mark that plan **blocked**: do NOT merge or clean up its worktree (preserve it for inspection), do NOT count the wave as successful, and surface the mismatch with recovery guidance to the user. The orchestrator — the worktree lifecycle owner — performs any base correction (e.g. recreate the worktree on `{EXPECTED_BASE}`); the sub-agent never does. Never proceed past a halted executor on the assumption it succeeded.

## ISOLATED-RUN RECOVERY — FAIL SAFE (#1292)

> **ISOLATED-RUN RECOVERY — FAIL SAFE (#1292):** When an isolated (worktree) run is *rejected* — the user declines to merge it, the orchestrator surfaces recovery guidance for a blocked/halted plan, or the run over-reached the requested scope — the worktree-isolation contract MUST hold through recovery. Do **NOT** propose continuing on `main`/the primary checkout as the default or recommended recovery path. Default to a **safe halt** and offer: (a) re-attempt in a **fresh, narrowly-scoped worktree**, or (b) inspect the retained worktree without merging. Discard/retirement requires the separate root custody handoff below. Any path that edits the primary checkout requires an **explicit, clearly-labeled confirmation** from the user first — editing `main` directly is never the proposed or default option for a run the user configured to be isolated.

## Accepted integration and manual retirement (ORCH-03)

The existing cleanup helper integrates accepted inputs and retains every worktree, branch ref and registration. Its supported CLI response is ordinary JSON: top-level `ok`, `plan`, and `result`; per-entry observations are in `result.entries`, unprocessed entries in `result.pending`. With `--exit-contract=v1`, held cleanup exits **1**, including after accepted integration. Missing `--manifest` exits 2; a manifest read failure exits 1 with `reason:manifest_read_failed` and no per-entry result. Preserve stdout, stderr and the actual exit. Neither `--raw` nor a successful invocation is a cleanup or acceptance verdict.

Read the observations independently:

- `integrated:true`, `status:integrated_retained`, reason `retirement_manual_root_handoff_required`: accepted integration was observed; manual retirement remains pending. A complete, identity-matched response for every requested entry permits independent project verification while reporting the cleanup exit 1. Keep all recovery/dispatch fields and the original manifest. Do not rerun integration merely to seek cleanup success.
- `integrated:false` (normally `status:blocked`): integration did not occur through this attempt; retain and hold progression. An accepted ancestor, a SUMMARY, a PID check, or a legacy `merged_removed` expectation does not replace the observed result.
- `integrated:null`, `status:integration_unknown_retained`: integration could not be established; retain and hold for root review. Do not infer that the branch was merged or unmerged.
- Another reason after `integrated:true` still reports observed integration, but changed/unknown custody needs root review before progression. Missing, duplicate, pending or mismatched entries, invalid JSON and unexpected exits also hold. No deletion, unlock, broad discovery or prune fallback is allowed.

The manifest is an array or an object with a `worktrees` array. Root acceptance uses the existing per-entry `retirement_authorization` object with `owner_id`, full immutable `accepted_head`, and a named independent `recovery_ref` that retains that accepted tip. The helper independently reads the existing native sibling `.worker.json` lifecycle record and checks completion, identity/path and fresh liveness. A manifest annotation, matching email, dead PID, age or ancestry alone grants no authority. `record-agent` and `quick-batch cleanup-entry` supply dispatch/scope metadata; they do not grant acceptance. If a harness does not provide the required native completed-owner evidence, preserve the hold; never fabricate a lifecycle record or add a registry, wrapper, scheduler or approval flag.

Only root may perform manual native Git retirement after accounting for the owner and **all writers**, including descendants, resumed agents, other threads and external processes. A one-PID record cannot establish that quiescence. Immediately before any action, root must bind the exact checkout, Git common directory, registration/lock state, branch and exact current HEAD to the reviewed entry; re-read tracked/untracked/ignored status and complete nested-checkout inventory. Unknown, unreadable, changing, locked or active work stays retained. Age, email and ancestor-only evidence do not authorize disposal.

Root must independently verify that a retained recovery reference outside the retiring branch actually retains the exact accepted/current tip and that any dirty, untracked, ignored or nested work has separate verified recovery. A recovery ref to commits does not preserve uncommitted data. Preserve recovery evidence, manifests, native owner/session records and logs. If the branch/HEAD, registration, status, writer set or recovery changes, stop and re-account rather than reusing stale evidence.

After those checks and explicit entry-specific retirement authority, root may use non-forced native removal for that exact registered checkout, verify its actual removal, then compare-and-delete only the exact branch ref with the freshly verified **expected old SHA**. A failed command stops the handoff; no force fallback, automatic unlocking, blanket branch deletion or repository-wide registration prune. A missing path does not prove registration retirement. Other registrations and owners remain outside that action. This workflow supplies no automatic retirement command sequence.

Keep implementation, integration, tests, review, project/phase product acceptance, manual retirement, installation and live acceptance separate in every report. Successful project verification does not prove retirement; retained work does not itself fail an otherwise accepted product gate.
